# migration-lab

Six schema migrations that have to run while the application is serving traffic, executed
against a real Postgres 16 with 200,000 orders and a writer that never stops. Each step reports
how long it took and **how long the writer waited**; a migration that finishes fast but blocks
the table for two seconds fails.

> **Recorded, not live.** CI runs every scenario, writes `report.json`, and publishes it as a
> static site. There is no database to connect to, no login, no cost.

Part of a three-repo system:

| Repo | Role |
| --- | --- |
| [`orders-service`](https://github.com/slayyyyer/orders-service) | the service whose schema this is |
| **migration-lab** | the migrations for that schema, proven under load |
| [`gcp-reference-platform`](https://github.com/slayyyyer/gcp-reference-platform) | the Terraform that would host it, never applied |

Live site: <https://slayyyyer.github.io/migration-lab/>

## The six scenarios

| # | Scenario | The failure it prevents |
| --- | --- | --- |
| 01 | [Add a column, backfill in batches, enforce `NOT NULL`](scenarios/01-add-column-batched-backfill/README.md) | `SET NOT NULL` scanning a hot table under `ACCESS EXCLUSIVE` |
| 02 | [Rename a column with expand/contract](scenarios/02-rename-column-expand-contract/README.md) | `RENAME COLUMN` breaking every running instance at once |
| 03 | [Change a type with a shadow column](scenarios/03-change-type-shadow-column/README.md) | `ALTER COLUMN … TYPE` rewriting 200k rows while writes queue |
| 04 | [Split a table with a foreign key](scenarios/04-split-table/README.md) | moving columns and dropping the originals in one deploy |
| 05 | [`CREATE INDEX CONCURRENTLY` vs the naive build](scenarios/05-concurrent-index/README.md) | a `SHARE` lock that stops every writer for the whole build |
| 06 | [A deliberately bad migration](scenarios/06-bad-migration/README.md) | *nothing* — it exists to prove the harness catches it |

Scenario 06 is the control. A lab full of good migrations says nothing about whether the
harness can tell good from bad, so one scenario is bad on purpose and counts as a pass only
when it is caught.

## How the harness decides

`scripts/run-lab.sh`, per scenario:

1. **Drop and recreate the database.** Every run starts empty; a leftover schema cannot make a
   previous failure look green.
2. **Apply the shared baseline and the deterministic seed** (`shared/baseline.sql`,
   `shared/seed.sql`, seeded PRNG at `SCALE`, default 200,000 orders).
3. **Fingerprint what must survive.** `checks.sql` runs in `before` mode and stores a checksum
   of the columns this scenario promises to preserve. Each scenario checksums *its own*
   invariant — a checksum over a column the migration is supposed to change would prove nothing.
4. **Start a writer.** A loop updates a row every 50 ms and records each wait.
5. **Apply each migration step** through the Flyway CLI, one `-target` at a time, timing each.
6. **Re-run the previous release's query** while the schema is mid-expand. If it breaks, the
   scenario fails even though the new schema is fine.
7. **Backfill**, if the scenario has one, in batches of 5,000 — each batch its own transaction.
8. **Re-check** in `checks.sql` `after` mode, then compare the worst writer wait with the
   scenario's `LOCK_BUDGET_MS`.

Statuses are deliberately distinct: `pass`, `fail`, `caught` (an expected failure the harness
detected), `not-caught` (a bad migration that slipped through — this is itself a failure), and
`error` (the harness could not run).

`report.json` is generated by Postgres with `json_build_object`/`json_agg`, not assembled in
bash, so there is no JSON escaping to get wrong.

## Run it yourself

```bash
# needs psql and a reachable Postgres; Docker works fine
docker run --rm -d --name lab-pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=postgres postgres:16-alpine

export PGURL=postgresql://postgres:postgres@localhost:5432/postgres
./scripts/get-flyway.sh          # pinned CLI, needs a JDK 17+
SCALE=20000 ./scripts/run-lab.sh # smaller scale for a first look
```

Set `FLYWAY_BIN` if the CLI is already on your PATH. The report is written to
`dist/data/report.json`; open `site/index.html` over a local server, or let CI publish it.

Point it at your own schema by editing `shared/baseline.sql` and the per-scenario assertions.
That is the part worth doing: the value is in the invariants, not the SQL.

## Layout

```
shared/baseline.sql        the orders schema, identical to orders-service V1
shared/seed.sql            deterministic 200k-order generator
scripts/run-lab.sh         the harness: measure, assert, report
scripts/get-flyway.sh      pinned Flyway CLI download
scenarios/NN-name/
  scenario.env             title, expected failure, lock budget, target hooks
  migrations/V*.sql        Flyway migrations, applied one target at a time
  backfill.sql             optional batched data step (not a migration — see below)
  previous-queries.sql     the previous release's read path
  checks.sql               mode-aware assertions
docs/diagrams/             Mermaid sources
site/                      the static report page
```

## Two deliberate deviations

**Backfills are not migrations.** A schema change is a version; a data backfill is an
operational step that must be resumable and interruptible. Running 200k updates inside one
Flyway transaction would hold a single long transaction — the thing this repo is trying to
avoid. The harness runs `backfill.sql` in separate transactions and stops when it returns 0, so
re-running it is safe by construction.

**`CREATE INDEX CONCURRENTLY` is not a Flyway migration either.** It cannot run inside a
transaction block, and Flyway wraps SQL migrations in one. Rather than hide that in a
configuration flag, the harness executes that statement directly. The exception is the lesson.

## What was verified, and what was not

| Check | Status |
| --- | --- |
| Terraform-style static review of every SQL file | done by hand, **not** by a parser |
| `bash -n` on both scripts | pass |
| Full scenario sweep against Postgres | **not run on the authoring machine** — no Docker or local Postgres was available |
| GitHub Actions run, `report.json`, published site | **not run** — the workflow is written and unexecuted |

The site says "recorded, not live" because the first honest run is the one CI produces. If a
scenario fails there, the failure is visible on the page rather than hidden in a badge: the
report is published with `if: always()`, and the job still fails so the run is red.

## Cross-references

- The schema is `orders-service`'s `V1__schema.sql`, so these migrations apply to the service.
- The `orders` and `customers` tables are the ones the GraphQL API pages through; index changes
  here are the ones that would matter under real query load.
- The Terraform repo's Cloud SQL module is what a real deployment would run these against —
  with a maintenance window, which is exactly the crutch this lab removes.
